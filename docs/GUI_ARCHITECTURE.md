# SQ8L GUI port: architecture

The original editor (Delphi VCL form `TplugEditForm`, 626×430) is almost entirely bitmap
based: a JPEG background, sprite strips (TAniGIF) for knobs, buttons, LEDs, the VFD
character set and the 7-segment program number, plus a few text elements (status bar,
program name edit box, popup menus, dialogs). The port reproduces it **pixel-exact** by
software-rendering into an RGB framebuffer; the plugin framework (DPF) only blits the
framebuffer and forwards input.

## Reference: the GUI oracle

`oracle/gui.py` + `oracle/gui_driver.py` run the ORIGINAL editor code headless in the
emulator (USER32/GDI on numpy framebuffers). `Editor()` opens it; `click(name)`,
`drag(name, dy)`, `popup_of(...)`, `idle(ms)`, `frame()` / `screenshot(path)`. Control
names come from the original form (`re/extracted/forms/TPLUGEDITFORM.txt`). Text is
rendered with macOS TrueType fonts (MS Sans Serif → Microsoft Sans Serif), so only text
pixels may differ from a real Windows XP; everything else is the original's own pixels.

## Layers (`src/gui/`, framework independent, namespace `sq8l::gui`)

1. **Graphics core**: `Bitmap` (RGB24, width×height), blits with transparency color keys,
   fills, simple lines; `Sprite` = frames of equal size. Assets in `src/gui/data/*.cpp`,
   generated by scripts from the ORIGINAL's decoded pixels (read from emulator memory after
   the original decoded its JPEG/GIFs) so that JPEG decoding differences cannot creep in.
2. **Controls** mirroring the original components, each with the same position/size as in the
   form, `paint(Canvas&)`, mouse handlers and hint text: `LcdDisplay` (TLCD3), `Knob`
   (TGraphKnobB), `GraphButton` (TGraphButton), `AniDisplay` (TAniDisplay), `Led`, `Image`,
   `Label/Panel` (status bar), `NameEdit` (program name).
3. **Editor logic**: port of `plugEdit` (TplugEditForm event handlers, menus, program
   selection, write/init/compare, options), `lcdControl` + `lcdSetup` + `paramEditor` (the VFD
   pages, parameter formatting and editing), `mouseJump`, `keyCapture` (as far as meaningful),
   dialogs (`uSelSingleForm`, `uMidiSelForm`, `uModInfoForm`, `uAboutForm`, `uMessageBox`).
   It talks to the engine through narrow interfaces (edit buffer / program bytes, library,
   synth status, settings).
4. **Platform interface** (`PlatformUi`): popup menus (data model + our own Windows-classic
   style renderer), modal dialogs, file open/save, timers (20 ms tick like the original's
   CsimpleTimer), mouse cursor warp (the "jumping mouse"), clipboard/keyboard capture.
   Implemented later by the DPF UI. On Windows the menus are real `TrackPopupMenu` menus,
   except that a menu split into columns (the program list, the longer LCD value lists) is
   not drawn in the host's dark theme by Windows, so `win/DarkMenu` owner-draws those from
   the theme parts USER32 would have used.

`EditorModel::render(Bitmap&)` composes the whole window exactly like the VCL paint order;
input arrives as `mouseDown/Move/Up/DoubleClick(x, y, buttons)` in form coordinates.

## Verification

C API (`tests/capi_gui*.cpp`) to create the editor model with a given program/state, inject
the same input sequence as the oracle driver, render, and compare pixels with the oracle's
screenshot (`tests/test_gui_*.py`). Tolerance: exact match outside text areas; text areas
are compared separately (string content via the original's captions/LCD buffers).
